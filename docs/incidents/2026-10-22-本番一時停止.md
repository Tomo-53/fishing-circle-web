# 本番サイト一時停止の記録（2026年10月22日）

| 項目 | 内容 |
|------|------|
| 停止日 | 2026年10月22日 |
| 停止した範囲 | 本番（Railway）のアプリ公開URL・MySQL の外部公開 |
| 状態 | 対応中（再開条件は §5 参照） |
| 記録者 | 運営（開発担当） |

---

## 1. 一言でいうと

**PHP 本体の重大な脆弱性**と、**サーバー会社 Railway への不正アクセス事件**が同じ時期に重なった。
本番サイトはどちらの影響も受けうる状態で、しかも Railway 側の事情で修正版を入れられなかった。
そのため、**修正できるまでの間、外部から入れないように一時的に公開を止めた**。

---

## 2. 止めた理由

### 理由①：PHP の重大な脆弱性「PHP2Shell」

- **CVE**: CVE-2026-109618 / CVE-2026-109619（深刻度 9.2 / 10、Critical）
- **公表・修正**: 2026年10月21日（前日の20日に情報が流出）
- **内容**: ログイン不要で、細工したリクエストを1つ送るだけでサーバー上で任意のプログラムを実行できる（遠隔コード実行）。
  さらに、同時刻の他の利用者のリクエスト内容（パスワード等）がメモリから漏れる可能性も指摘されている。
- **本サイトへの影響**: 本番の PHP は **8.2.34**。修正版 **8.2.35** の1つ手前で、**影響を受けるバージョン**だった。
- **重要な点**: Laravel より前の段階（PHP 本体）で起きるため、アプリ側の権限管理（4段階ACL）やバリデーションでは防げない。

> たとえ: 建物の鍵（ACL）はしっかりしていても、建物の壁そのものに穴が開いている状態。

### 理由②：Railway への不正アクセス事件

- **発生**: 2026年10月21日、Railway が「利用者の環境変数を保管するシステム」への不審なアクセスを検知。
- **内容**: 第三者が利用者の環境変数（パスワード等の秘密情報）にアクセスし、一部は中身を解読された可能性があると Railway が発表。
- **Railway の対応**: 全利用者のデプロイを一時停止し、全環境変数の変更（ローテーション）を呼びかけ。
- **本サイトへの影響**: 本番の環境変数に以下が保存されているため、漏えいした可能性がある。
  - DB の接続情報（パスワード）
  - `APP_KEY`（Laravel の暗号化キー）
  - Gmail のアプリパスワード（会員へのメール送信用）

### 理由③：修正したくても修正できない状況だった

- PHP を修正版にするには再デプロイが必要だが、**Railway のデプロイが停止中**で入れ替えられなかった。
- 一方で、**すでに動いているサイトは普通に外部から開ける状態**だった（Railway の停止は「新しく入れる仕組み」のみで、稼働中のサーバーは止まっていなかった）。
- さらに、**MySQL がインターネットから直接接続できる設定（TCP Proxy）になっていた**。
  理由②で DB パスワードが漏れていれば、アプリを経由せず会員データベースへ直接入られる危険があった。

**→ 「穴が開いている」「合鍵が盗まれたかもしれない」「修理業者が来られない」の3つが重なったため、入口を閉じる判断をした。**

---

## 3. 起こりえた被害（止めなかった場合の最悪ケース）

実際に攻撃を受けた証拠は確認していない。以下はあくまで「起こりえた」被害。

| 対象 | 起こりえたこと |
|------|---------------|
| 会員情報（`users`） | 氏名・メールアドレス・学年/役職の流出。弱いパスワードの割り出し |
| ログイン情報（`sessions`） | IPアドレスの流出、他人へのなりすましログイン |
| グループ・権限（`groups` / `user_groups`） | 所属・権限の流出、権限の書き換え（攻撃者がオーナー権限を得る等） |
| Gmail アプリパスワード | サークルのアドレスから会員へ詐欺メールを送られる |
| サイト全体 | 改ざん、データ削除、他サイト攻撃の踏み台 |

## 4. 実施した対応

### Railway（本番）

- [x] 本番の PHP バージョンを確認（8.2.34 = 影響あり）
- [ ] アプリの公開ドメインを削除（外部からアクセス不可にする）
- [ ] MySQL の TCP Proxy（外部公開ポート）を削除
- [ ] MySQL の公開ドメインを削除
- [ ] Gmail のアプリパスワードを取り消し
- [ ] Railway からの影響通知メールの有無を確認

> 公開を止めるため、デプロイ自体の削除ではなく「公開ドメインの削除」を選んだ。
> デプロイを削除すると、Railway のデプロイ停止中は復旧できなくなるため。

### リポジトリ（ブランチ `claude/dazzling-ride-o69ysb`）

- [x] `src/composer.json`: PHP 要件を `^8.2.35` に変更し、本番（Railpack）が修正版 8.2.35 を選ぶようにした
  - 最初は `~8.2.35 || ~8.3.36 || ...` と指定したが、Railpack は `||` を含む指定を解釈できずビルドが失敗するため修正した
- [x] `docker/php/Dockerfile`: ローカル環境を `php:8.2.35-fpm` に固定
- [x] `docker/php/security.ini` / `src/public/.user.ini`: 攻撃経路として報告されている `session.upload_progress` を無効化
- [x] `SETUP.md` §4.5 に確認手順を追記

## 5. 再開の条件と手順

以下が**すべて**そろったら公開を再開する。

1. [ ] Railway のデプロイが再開している（[status.railway.com](https://status.railway.com/) で確認）
2. [ ] 本番の PHP が **8.2.35 以上**になっている（サービス画面の `php@x.x.x` 表示で確認）
3. [ ] 秘密情報をすべて新しくしている
   - [ ] DB パスワード
   - [ ] `APP_KEY`（変更すると全員ログアウトされるが問題ない）
   - [ ] Gmail アプリパスワード（新規発行して `MAIL_PASSWORD` に設定）
4. [ ] 不審なデータがないか確認している
   - [ ] `user_groups` に身に覚えのない権限レベル4（オーナー）がいない
   - [ ] `users` に不審なアカウントが増えていない
5. [ ] MySQL の外部公開（TCP Proxy）は**付け直さない**（アプリは内部通信で接続するため不要）

再開時は、アプリの Settings → Networking → **Generate Domain** で公開URLを再発行する。
URL が変わった場合は会員へ周知する。

## 6. 学び・今後の改善

- **PHP のバージョンは自動任せにしない。** `^8.2` のような緩い指定だと、脆弱な版のまま動き続ける。修正版を明示的に要求する。
- **DB をインターネットに公開しない。** アプリと DB は Railway 内部通信（Private Networking）で十分。TCP Proxy は使うときだけ一時的に付ける。
- **秘密情報は「漏れたら差し替える」前提で管理する。** どこに何が保存されているかを把握しておく（今回は Railway の Variables）。
- **依存パッケージの脆弱性も定期確認する。** 本件の調査中に `composer audit` で Laravel・Symfony 等に既知の脆弱性が48件見つかった（別タスクで対応）。
